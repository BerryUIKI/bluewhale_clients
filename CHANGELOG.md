# Changelog

All notable changes to the Bluewhale clients are documented in this file. The project follows [Semantic Versioning](https://semver.org/spec/v2.0.0.html) and [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

## [Unreleased]

### Added

- Repository scaffolding: workspace manifests, toolchain pinning, contribution and security policies, and editor configuration.
- Phase 3.1 shell: a Tauri 2 Windows application with a minimal command boundary; a shared React + TypeScript interface with hash routing, design tokens for light and dark appearance, English and Simplified Chinese resources, persisted language and appearance preferences, localized command-error mapping, and a recovery screen for render failures.
- `clients-ipc`: a typed `CommandError`, the `app_info` command, and TypeScript bindings generated by tauri-specta. A Rust test fails when the committed bindings drift. The crate embeds a Windows application manifest so its binaries and test harnesses load Common Controls version 6.
- `clients-runtime`: the application service that supplies build and platform metadata to the command boundary.
- ESLint, Prettier, TypeScript, and Vitest configuration in `packages/config`, 24 interface tests with React Testing Library, and CI workflows for the interface and the Windows desktop checks.
- Recorded MPL-2.0 and `Apache-2.0 WITH LLVM-exception` exceptions for the approved Tauri 2 transitive dependencies in `deny.toml`.
- Phase 3.2 ledger management: a device-local catalog of ledger descriptors and the active selection, written atomically and containing no key material; first-run setup and add-ledger forms with the ledger name, emoji, reporting currency, time zone, and localized default account and category names; per-ledger SQLCipher databases initialized through the core ledger use case; switching; and non-destructive removal that keeps the database and key files.
- `clients-platform`: the Windows key protector. Ledger database keys are 256-bit random values protected with user-scoped DPAPI, using the ledger identity as additional entropy, and stored beside the ledger database as protected blobs rather than raw keys.
- `clients-runtime` ledger services: the catalog store, the ledger service (create, open, switch, remove, active profile), a system clock, and a UUIDv7 source. Six core crates are pinned from the public repository at a full revision and recorded with the annotated `v0.1.0` tag in `docs/development/core-pin.md`.
- `clients-ipc` ledger commands: `ledger_list`, `ledger_create`, `ledger_switch`, `ledger_remove`, and `ledger_active_profile`, with typed DTOs, camelCase fields, and error details that carry a local data path for recovery. The generated bindings were regenerated and the drift test covers them.
- Interface ledger screens: first-run setup with React Hook Form and Zod validation, a ledger manager that shows store status with retry and a removal confirmation dialog (Radix AlertDialog), a ledger switcher in the shell, and an overview that shows the active ledger profile or its recovery state.
- Test coverage for the ledger work: 16 runtime tests (creation, reopening, switching, missing database, missing key, unreadable key, wrong key, non-destructive removal, input validation, corrupt catalog) and 36 interface tests, plus a live WebView2 check of setup, switching, store recovery, and removal.
- Recorded `blessing` and `WTFPL` licenses for the bundled SQLCipher sources and allowed the core git source in `deny.toml`.
- A single-instance guard for the desktop application: a second launch focuses the running window and exits, so two processes cannot write the same data directory.
- Phase 3.3 master data: accounts with an optional opening balance, tags, a household-member owner, a custom group, a note, and hidden and net-worth flags; custom account groups; two-level expense and income categories and their groups; tags with colors and descriptions; and counterparties with three kinds. Every record supports create, edit, archive, and restore, and archived records stay visible behind a show-archived toggle.
- `clients-runtime` master-data service: one snapshot read plus mutations composed from the approved core use cases, with append-only manual order, archived records kept in the snapshot, and typed errors for validation, missing records, archived groups, and kind mismatches.
- `clients-ipc` master-data commands: `master_data`, `account_create`, `account_update`, `account_group_create`, `account_group_update`, `category_group_create`, `category_group_update`, `category_create`, `category_update`, `tag_create`, `tag_update`, `counterparty_create`, and `counterparty_update`, with DTOs for every record and request. The bindings were regenerated and the drift test covers them.
- Interface master-data screens with accessible modal forms (Radix Dialog, React Hook Form, Zod), a reporting-currency default for new accounts, navigation entries, and complete English and Simplified Chinese resources.
- Test coverage for the master-data work: 11 runtime tests, IPC error-mapping and enum round-trip tests, and 17 interface tests, plus a live WebView2 check of creation, archiving, restoring, and persistence after reload.
- Phase 3.4 transactions: a history grouped by ledger-local day with search and filters for text, kind, account, category, tag, counterparty, and an inclusive date range; an editor for expenses, incomes, and transfers with exact source and destination amounts, tags, one counterparty, and a note; soft deletion and a recovery view; and opening balances shown in the history without an edit action.
- `clients-runtime` transaction service: list, get, create, update, soft delete, and restore composed from the approved core use cases, with occurrence times interpreted in the ledger time zone and entries carrying the UTC instant plus the ledger-local date and time.
- `clients-ipc` transaction commands: `transaction_list`, `transaction_get`, `transaction_create`, `transaction_update`, `transaction_delete`, and `transaction_restore`, with exact decimal amount strings, currency scales, reporting directions, and DTOs for every request. The bindings were regenerated and the drift test covers them.
- The transaction editor defaults its date and time to the ledger time zone, reveals the received-amount field only for cross-currency transfers, warns when a current reference is archived, and clears kind-specific fields when the kind changes.
- Test coverage for the transaction work: 11 runtime tests, 3 IPC tests, and 10 interface tests, plus a live WebView2 check of recording, filtering, editing, deleting, restoring, and persistence after reload.

### Changed

- Repository status is pre-alpha. Phase 3.4 is complete; reports, sync, the Android application, and the ledger features beyond transactions are not implemented yet.
- The Rust workspace now builds the core persistence crate with vendored SQLCipher and OpenSSL, so cargo commands need the native Windows Perl and `nmake` environment.

### Security

- The desktop application uses a strict content security policy, with a separate development policy for the Vite dev server, and its only capability is `core:default`: no shell, process, or file-system permissions. The Tauri `devtools` feature is not enabled.
- Ledger keys are protected with user-scoped DPAPI bound to the ledger identity. The catalog holds descriptors and the active selection only; key files contain DPAPI blobs, never raw keys. Removing a ledger from the device leaves its files in place and never deletes financial data.
